# Проект 2. Cashback Merge

Мини-игра в духе 2048 на поле `4x4`. На поле появляются плитки с кэшбэком,
две одинаковые объединяются в следующую:

```text
1% + 1% = 2%    2% + 2% = 4%    ...    16% + 16% = 32%
```

У игрока ограниченное число ходов, цель — собрать максимальный кэшбэк.
Вторая часть проекта — конфиг кампании и batch-симуляция: какая доля игроков
получает максимальную награду и укладывается ли она в допустимый лимит.

Задание — в [TASK.md](TASK.md), работа с шаблоном — в [HELP.md](HELP.md).

### Симуляция кампании

```bash
./gradlew run --args="simulate --config config/campaign.example.json --players 10000 --strategy random --seed 42 --output report.md"
```

|---|---|---|

Примеры отчётов (10 000 игроков, seed 42):

| Конфиг | Лимит ходов | Доля максимальной награды | Статус | Отчёт |
|---|---:|---:|---|---|

около 9%, при 42 — около 15%, при 45 — уже больше 25%.

### Если конфиг некорректен

Программа перечисляет **все** ошибки сразу, с путём к полю, и завершается
с кодом `3`:

```text
Конфиг кампании некорректен:
  - movesLimit: должен быть больше 0, получено 0
  - spawnRules[1].cashback: правило для 1% уже задано
  - spawnRules: сумма вероятностей должна быть ровно 1, получено 0.95
  - rewardTable: нужна хотя бы одна строка таблицы наград
```

## Конфиг кампании

Пример — [config/campaign.example.json](config/campaign.example.json).

| Поле | Что | Правила |
|---|---|---|
| `boardSize` | сторона поля | необязательное, по умолчанию и пока только `4` |
| `movesLimit` | сколько ходов, изменивших поле, есть у игрока | целое `> 0` |
| `spawnRules` | `cashback` и `probability` новой плитки | не пусты; вероятности `> 0`, в сумме ровно `1`; кэшбэк не повторяется |
| `rewardTable` | `cashback` → `reward` | не пуста; награда `>= 0`; кэшбэк не повторяется |
| `maxRewardCashback` | плитка с максимальной наградой | есть в `rewardTable` |
| `maxRewardAllowedRate` | допустимая доля игроков с максимальной наградой | от `0` до `1` |

Проценты, вероятности и награды записываются **строками**: `"0.85"`, а не `0.85`.
Число без кавычек — ошибка конфига, а не молчаливое чтение в `double`.
Неизвестные поля тоже ошибка (так ловятся опечатки), кроме комментариев
`_note` и `_comment`.

Кэшбэк (`cashback`, `maxRewardCashback`) — целая **степень двойки**: `1`, `2`, `4`,
`8`, ... Другие значения слиянием не получить, поэтому `3` или `1.5` — ошибка конфига.

### Решения

**Точная арифметика без лишнего.** Вероятности и награды — `BigDecimal`: в
`double` `0.7 + 0.2 + 0.1 != 1.0`, и проверка «сумма вероятностей равна 1»
перестала бы быть проверкой (это показано в `CampaignConfigLoaderTest`).
Кэшбэк и score — целые (`int` и `long`): кэшбэк всегда целая степень двойки, а
score — сумма таких значений, так что `BigDecimal` для них ничего не даёт.
Степень двойки — инвариант `Cashback`: некорректную плитку нельзя создать ни из
конфига, ни из кода.

**Неизменяемая модель.** `Board` и `GameState` не меняются: любое изменение
возвращает новый объект. Инварианты (клетка в границах, одна плитка на клетку,
`movesLimit > 0`) проверяются в конструкторах, так что некорректное состояние
нельзя создать даже из кода. Ход возвращает новое состояние, поэтому «изменил ли
ход поле» — это просто сравнение полей до и после.

**Валидация в два этапа.** Сначала разбор (`RawConfigConverter`): есть ли
обязательные поля и числа ли в них. Потом бизнес-правила в конструкторе
`CampaignConfig`: непустые правила,
сумма вероятностей, уникальность. На каждом этапе собираются все ошибки, чтобы
конфиг можно было исправить за один заход. Невалидный `CampaignConfig` создать
нельзя ни из файла, ни из кода.

**Seed и случайность.** Случайность изолирована в `TileSpawner` — движок ходов
работает с интерфейсом, а в тестах подставляется предсказуемая реализация. `RandomTileSpawner` использует `SplittableRandom(seed)`: его алгоритм
зафиксирован в JDK, поэтому одинаковый seed даёт одинаковое поле на любой машине.
На каждую плитку — ровно два обращения к генератору: клетка, затем кэшбэк.
Свободные клетки перебираются в фиксированном порядке (построчно).

**Взвешенный выбор без `double`.** `SpawnDistribution` — категориальное
распределение: вероятности переводятся в целые веса с общим знаменателем
(`0.85`/`0.15` → `85`/`15` из `100`), берётся случайное целое из `[0, 100)` и
находится отрезок накопленных весов, куда оно попало.

## Движок ходов (MR2)

```text
MoveEngine.applyMove(state, direction) -> MoveResult
```

Ход — две независимые части:

| Часть | Где | Случайность |
|---|---|---|
| Движение: сдвиг и слияния | `BoardShift`, `LineMerger` | нет |
| Появление новой плитки | `TileSpawner` | да, по seed |

**Одна линия — один алгоритм.** Все четыре хода сводятся к сдвигу линии «к
началу». `Direction` только нарезает поле на линии и задаёт порядок клеток:
для `LEFT` строка читается слева направо, для `RIGHT` — справа налево, для `UP`
столбец сверху вниз, для `DOWN` — снизу вверх.

**Слияние линии** (`LineMerger`). Пустые клетки выкидываются, затем линия
читается одним указателем: если плитка равна следующей, они сливаются, и
указатель перескакивает **через обе**; иначе плитка остаётся, указатель идёт на
одну дальше.

**Почему плитка не сливается дважды.** Получившаяся при слиянии плитка уже
записана в результат, а указатель стоит за обеими исходными — её больше никто
не читает. Поэтому `[1, 1, 2, _] -> [2, 2, _, _]`, а не `[4, _, _, _]`.

```text
[1, 1, _, _] -> [2, _, _, _]
[1, 1, 1, _] -> [2, 1, _, _]
[1, 1, 1, 1] -> [2, 2, _, _]
[2, 2, 4, 4] -> [4, 8, _, _]
```

**Ход без изменений.** Если после сдвига поле равно исходному, ход ничего не
сдвинул и не слил: состояние возвращается как есть, лимит не тратится, плитка
не появляется.

**Ровно одна новая плитка.** После изменившего поле хода `MoveEngine` вызывает
`TileSpawner` один раз и проверяет результат: добавлена ровно одна плитка,
остальные на месте. Клетка новой плитки возвращается в `MoveResult.spawnedAt`.

**Score.** За каждое слияние прибавляется значение получившейся плитки:
`[2, 2, 4, 4]` даёт `4 + 8 = 12`. Сдвиг без слияний очков не даёт.

**Конец партии.** Плитка `32%` игру не завершает — партия идёт до `movesLimit`
изменивших поле ходов. Есть ещё один случай, которого нет в условии: поле
заблокировано, и ни один ход ничего не меняет. Лимит тогда потратить нечем, и
без этого правила симуляция в MR3 зависла бы. `MoveEngine.isGameOver(state)`
учитывает оба случая, `MoveEngine.availableMoves(board)` возвращает ходы,
которые что-то меняют. Сам `applyMove` отказывает только при исчерпанном лимите:
на заблокированном поле ход просто ничего не меняет (это обычный ход без
изменений), а проверять доступные ходы перед каждым ходом значило бы делать
четыре лишних сдвига поля на каждый ход симуляции.

**Что менять, если попросят.** Правило появления плитки — `spawnRules` в
конфиге (или своя реализация `TileSpawner`); лимит ходов — `movesLimit` в
конфиге. Код движения (`BoardShift`, `LineMerger`) при этом не меняется.

## Награды и симуляция (MR3)

**Награда по максимальной плитке** (`RewardTable`). Tier — строка таблицы с
наибольшим кэшбэком, не превышающим максимальную плитку игрока: плитка `16%` даёт
tier `16` (награда 500), `64%` — tier `32` (старше в таблице нет), `1%` — без
награды. Максимальную награду получает тот, чья плитка не меньше
`maxRewardCashback`.

**Партия игрока** (`GameRunner`). Стратегия возвращает не один ход, а порядок
предпочтения всех четырёх. Делается первый ход, который меняет поле; если не
меняет ни один, поле заблокировано и партия окончена. Стратегия `random`
перемешивает ходы, поэтому выбирает равновероятно среди ходов, которые что-то
меняют. Новая стратегия (например, `greedy-score`) — это ещё одна реализация
`Strategy` и строка в `Strategies`.

**Воспроизводимость.** Из `seed` создаётся главный `SplittableRandom`, и каждый
игрок по очереди получает от него свой генератор (`split()`). У игрока он ещё раз
делится: отдельно на появление плиток и на решения стратегии, — поэтому смена
стратегии не меняет последовательность плиток и стратегии можно честно
сравнивать на одном seed. В отчёте нет времени и других меняющихся данных:
одинаковые входы дают байт в байт одинаковый отчёт.

**Проверка ограничения** (`ConstraintStatus`). `actualMaxRewardRate <=
maxRewardAllowedRate` проверяется без деления: `count <= allowed × players` в
`BigDecimal`. Деление `1/3` дало бы бесконечную дробь, и на самой границе
результат зависел бы от округления. `20` из `100` при `0.20` — `OK`, `21` — `FAILED`.

**Отчёт** (Markdown или JSON) содержит конфиг, seed, число игроков, стратегию,
распределение максимальных плиток и наград (все tier, даже без игроков), средний
и максимальный score, долю максимальной награды с погрешностью и статус. В JSON
дробные числа — строки, как в конфиге.

### Математическая модель

| Понятие | Где в коде |
|---|---|
| [Категориальное распределение](https://en.wikipedia.org/wiki/Categorical_distribution) | `SpawnDistribution`: выбор плитки по накопленным весам (inverse transform sampling), только на целых весах вместо `double` |
| [Метод Монте-Карло](https://ru.wikipedia.org/wiki/Метод_Монте-Карло) | `Simulator`: доля максимальной награды оценивается частотой по многим случайным партиям |
| [Закон больших чисел](https://ru.wikipedia.org/wiki/Закон_больших_чисел) | частота сходится к настоящей вероятности с ростом числа игроков, но только при большом их числе |
| [Random seed](https://en.wikipedia.org/wiki/Random_seed) | seed полностью задаёт последовательность случайных чисел — и плитки, и решения стратегии |

**Погрешность оценки.** Доля по `n` игрокам — оценка, а не точное значение. Её
95% доверительный интервал — `p ± 1.96·√(p(1−p)/n)`: погрешность убывает как
`1/√n`, и чтобы уменьшить её вдвое, нужно вчетверо больше игроков. При 10 000
игроков и доле 15% это около ±0.7%. Поэтому статус — эмпирический результат для
конкретного конфига, seed, числа игроков и стратегии, а не математическая
гарантия: если доля близка к порогу, стоит увеличить `--players` или проверить
несколько seed.
